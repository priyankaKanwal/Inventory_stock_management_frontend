01 / Executive view

What this project is today

The application is an inventory operations client with lazy-loaded feature modules, root-provided services, paginated REST integration, route guards, and task-aware UI controls. There is no backend or model-training code in this repository.

9Lazy feature areasDashboard, products, categories, suppliers, tasks, orders, customers, predictions, users
5Application rolesSuper admin plus inventory/order manager and staff roles
41API operationsService methods across auth, inventory, orders, tasks, users, and predictions
2Prediction modesOrder-based ETA and manual what-if simulation
✓
Implemented in the client

Authentication screens, guarded lazy routes, CRUD screens, search and pagination, order state transitions, task delegation UI, typed HTTP services, bearer-token injection, and 401 refresh/replay.

!
ABAC verdict

Task-based record helpers create an ABAC-shaped UI gate, but this is not a complete server-enforced ABAC engine. Direct URLs and backend authorization still need protection.

×
AI / ML verdict

The frontend calls prediction endpoints and renders results. No model, training pipeline, feature store, or inference implementation is present in this repository.

04 / User workflows

End-to-end flows and function callings

Each flow below shows the UI trigger, component method, service method, HTTP operation, and the state that changes after a response. Source paths are included so the map can be followed in the code.

Authentication and session lifecycle

Login stores the returned access token, role, username, and optional user id in local storage. The interceptor uses the token for subsequent API calls and refreshes it after a non-auth 401.

01Submit loginLoginComponent.onSubmit() validates email/password.
02Call auth serviceAuthService.login(data) posts credentials.
03Persist sessionToken, role, username, and user id enter localStorage.
04Enter shellrouter.navigate(['/dashboard']) activates guarded layout routes.
LoginComponent.onSubmit()
  -> AuthService.login(loginData)
  -> POST /api/v1/auth/login
  -> localStorage: access_token, role, username, user_id
  -> Router.navigate(['/dashboard'])
Signup, logout, and refresh branches

SignupComponent.signup() calls AuthService.signup() and POST auth/register; success returns to login after a short delay.

SidebarComponent.logout() calls AuthService.logout(), clears session state, and navigates to login. The separate LoginComponent.logout() method only removes local keys and is not referenced by the active template.

A protected request receiving 401 enters authInterceptor, calls AuthService.refreshToken(), stores the rotated token, and replays the original request. Refresh failure clears the session and redirects to login.

Order status state machine

ORDER_PLACED -> CONFIRMED or CANCELLED; CONFIRMED -> PROCESSING, AWAITING_STOCK, or cancellation; PROCESSING -> PACKED, AWAITING_STOCK, or cancellation.

AWAITING_STOCK -> SUPPLIER_ORDER_PLACED or cancellation; SUPPLIER_ORDER_PLACED -> STOCK_RECEIVED or cancellation; STOCK_RECEIVED -> PROCESSING; then PACKED -> SHIPPED -> OUT_FOR_DELIVERY -> DELIVERED. The client mirror is defined in orders.component.ts:16-28.

06 / Authorization

RBAC is explicit; ABAC is task-scoped and client-side

Role helpers answer “may this role enter or manage a broad area?” Task helpers answer “does this staff member have an active assignment for this record?” The second question is not currently a secure backend boundary.

!
ABAC status: partial / UI-only

There is no ABAC policy engine, policy store, XACML/OPA layer, or backend enforcement code in this repository. The implemented mechanism is a set of client functions that derive attributes from task rows.

×
Security consequence

localStorage roles and visibility checks are not sufficient authorization. A user can bypass a hidden button by navigating directly to a route, so the backend must independently enforce every mutation.

Authorization call details and gaps

currentRole() reads localStorage.role; roleGuard reads the same key and compares it with route.data.roles. Sidebar getters are a UI mirror of those route rules.

canEditRecord(tasks, type, id) and canCreateRecord(tasks, type) only return true for staff roles. They are not called by the product add/edit route guard or form, so a hidden action does not prevent a direct form URL.

The ROUTE_ROLES map exists in roles.ts but is currently unused by the layout route module, which defines local role arrays instead. This is a maintainability and policy-consistency issue.
